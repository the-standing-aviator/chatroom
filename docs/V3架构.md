# V3 架构讨论稿（规模 / 分布式）

> 状态：**讨论稿，未定稿**。目标是把「单机 → 分布式」想清楚再动手写代码。
> 对应里程碑：V3 规模（分布式）——多节点 + 消息中间件 + 网关 + 分片。

## 1. 目标与根本问题

单机版（V1/V2）的隐含假设：**所有在线用户都在同一个进程内存里**（`sessions map`），广播 = 遍历 map 投递。这个假设在单机成立，但单机有物理天花板：

- **文件描述符 + 内存**：一个 TCP 连接 = 一个 fd + 一个 goroutine 栈 + 读写 buffer，粗略按每连接 10–50KB 算，百万在线 ≈ 10–50GB 内存，先于 CPU 撑不住。
- **CPU / 网络带宽**：百万用户每秒各发一条，扇出就是百万次写 socket。
- **单点故障**：一台机器挂了全体离线。

所以百万在线的解法不是「一台更强的机器」（垂直扩展有极限），而是「很多台普通机器分担连接」（水平扩展）。

## 2. 三根轴：别混

1. **代码分层**：同一进程内 `.go` 文件怎么组织成包（编译期边界）。
2. **进程 / 部署分层**：哪些部分拆成独立进程/独立机器，通过网络通信（运行期边界）。
3. **逻辑分层**：概念上的职责划分（接入 / 路由 / 状态 / 存储），可以用**包**实现（单机），也可以用**独立服务**实现（分布式）。

V3 要做的事，本质是**把某些逻辑职责从「包边界」升级成「进程边界」**。下面第 3、4 节分别从这两根轴画图。

## 3. 部署拓扑（进程 / 服务分层）

```
                            客户端 × N
                               │  TCP（自定义长度前缀 JSON 帧）
                               │
                        ┌──────▼──────┐
                        │  负载均衡器   │  L4/L7：把连接均匀分到各接入节点
                        └──────┬──────┘
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
       ┌────────────┐   ┌────────────┐   ┌────────────┐
       │ 接入节点 G1 │   │ 接入节点 G2 │   │ 接入节点 G3 │   无状态，可水平扩展
       └─────┬──────┘   └─────┬──────┘   └─────┬──────┘
             │                │                │
             └──────────┬─────┴──────────┬─────┘
                        ▼                ▼
                 ┌────────────┐    ┌────────────┐
                 │    NATS    │    │    Redis    │
                 │  消息总线   │    │  在线状态    │
                 │ (跨节点分发) │    │ user → node │
                 └─────┬──────┘    └────────────┘
                       │  (可选：消息旁路落库，做全量消息日志)
                       ▼
                 ┌────────────┐
                 │ PostgreSQL  │   users + messages（持久化）
                 └────────────┘
```

| 组件 | 职责 | 单机版对应 |
|------|------|-----------|
| 接入节点（Gateway） | 维持 TCP 长连接、编解码协议、把消息路由进/出 | 就是现在的 `internal/server` 拆成独立进程 |
| NATS | 跨节点分发（广播扇出 / 私聊定向投递） | 无（单机进程内 `sessions map`） |
| Redis | 在线状态 `user → node` 映射 | 无（单机进程内 `sessions map`） |
| PostgreSQL | 持久化用户 + 消息 | `internal/store` 的 SQLite 实现换掉 |
| 负载均衡器 | 把客户端连接分散到各接入节点 | 无（单机单地址） |

## 4. 代码包结构（软件结构分层）

```
communicate/
├── cmd/
│   ├── gateway/      # 接入层入口（V3 主入口，无状态可水平扩展）
│   ├── server/       # 单机入口（过渡期保留，V3.2 跑通后退役）
│   ├── client/       # 交互客户端
│   └── bench/        # 压测客户端
├── internal/
│   ├── protocol/     # 帧编解码（不变，各进程共用）
│   ├── gateway/      # 接入层：连接/会话/广播（← 由 internal/server 演进重构）
│   ├── bus/          # 消息总线客户端（新增，NATS 实现）
│   ├── presence/     # 在线状态（新增，Redis 实现）
│   ├── store/        # 持久化（SQLite 实现 → PostgreSQL 实现，接口不变）
│   └── auth/         # 鉴权（bcrypt → JWT）
```

对照现状的演进路径：

| 现状（V2） | V3 目标 | 变化性质 |
|-----------|---------|---------|
| `internal/protocol` | 不变 | 共用，零改动 |
| `internal/server` | `internal/gateway` | **拆进程**：连接/会话/广播逻辑整体搬到接入层进程 |
| （无，逻辑藏在 `sessions map`） | `internal/bus` | **新增包 + 新增外部进程**（NATS 客户端） |
| （无，逻辑藏在 `sessions map`） | `internal/presence` | **新增包 + 新增外部进程**（Redis 客户端） |
| `internal/store`（SQLite 实现） | `internal/store`（PostgreSQL 实现） | **只换实现**，接口不变 |
| `internal/server/auth.go`（bcrypt） | `internal/auth`（JWT） | 鉴权逻辑独立成包，方案换 JWT |

### 接口抽象原则（ports & adapters）

`bus` / `presence` / `store` 三个包都定义成**接口**，各配两套实现：

| 包 | 内存实现（standalone / 单测） | 真实实现（分布式） |
|----|------|------|
| `store` | 现有 SQLite（已走接口，可再加纯内存实现） | PostgreSQL |
| `bus` | 进程内直发（等价现状 `sessions map` 广播） | NATS |
| `presence` | 进程内 map | Redis |

`store` **已经是这个模式**（`store.go` 接口 + `sqlite.go` 实现），这正是「换 PG 只写一个实现」轻松的原因；`bus` / `presence` 照葫芦画瓢。带来的收益：① 单机模式 = gateway 挂内存实现、分布式 = 挂真实实现，**同一份代码**（第 7 节 Q5 由此解决）；② 单测用内存实现，不依赖真实中间件；③ V3 可小步演进——先单机跑内存实现（等价现状零风险），再逐个换真实实现。

## 5. 关键设计决策

### 5.1 消息总线：倾向 NATS

| 方案 | 优势 | 劣势 |
|------|------|------|
| Redis Pub-Sub | 最轻 | 消息不持久化、订阅者断开就丢；扩容要上 Cluster |
| **NATS** | 低延迟、主题订阅、水平扩展，天生为扇出设计 | 核心是 fire-and-forget（持久化要靠 JetStream） |
| Kafka | 强持久化 + 重放 + 吞吐巨大 | 延迟更高、运维重，适合日志而非实时下发 |

倾向 **NATS**：实时聊天扇出，低延迟、运维轻。Kafka 留作「消息全量落库的旁路日志」可选，不进主路径。

### 5.2 在线状态：Redis + TTL 兜底

单机 `sessions map` 挪到 Redis 的 `user → node` 映射。关键坑：**节点挂了，映射变脏数据**。解法：在线状态带 TTL，接入节点周期性心跳续期；节点一挂，TTL 到期自动失效，客户端重连后重新注册。可接受「TTL 窗口期内误判在线」的最终一致性代价。

### 5.3 存储：SQLite → PostgreSQL

直接解决 P2-4（`SetMaxOpenConns(1)` 单连接串行）。PostgreSQL 多连接池 + 并发读写，天然适配多节点写。`internal/store` 接口不变，只换实现。

### 5.4 鉴权：bcrypt → JWT

单机版登录时 bcrypt 校验 + 查库。分布式下任何接入节点都要能验身份，改成登录时签发 JWT（无状态 token），后续请求带 token 即可验，不用每次查库。

### 5.5 消息路由：广播扇出 vs 私聊定向

- **公聊/广播**：接入节点把消息发到 NATS 的广播主题，**所有接入节点**订阅该主题、各自下发给本节点内的订阅者。节点数远小于用户数，扇出成本可控。
- **私聊**：查 Redis `user → node`，把消息投到目标节点对应的 NATS 主题（定向投递），只有目标节点消费。

## 6. 落地顺序（每步可验证）

1. **V3.1 存储迁移**：`internal/store` 换 PostgreSQL 实现，单机先跑通，解决 P2-4，验证换库不破坏现有功能（跑现有 `_test.go` + 压测）。
2. **V3.2 状态外置 + JWT**：在线状态抽到 `internal/presence`（Redis）、鉴权抽到 `internal/auth`（JWT），仍是单机，但把状态从进程内存搬出去，为多节点铺路。
3. **V3.3 引入 NATS + 拆接入层**：新增 `internal/bus`（NATS）+ `internal/gateway`（拆出接入层）+ `cmd/gateway`，跑两个节点，跨节点私聊/公聊走通。
4. **V3.4 网关 + 水平扩展压测**：加 LB，压测多节点在线数与延迟，验证水平扩展收益。

## 7. 已决问题（2026-10-31 讨论确定）

1. **NATS 不用 JetStream**：NATS 只做投递传输，持久化唯一事实源是 PostgreSQL。发送方 gateway 异步落库（复用 `saveLoop`）同时 pub 到 NATS；接收方只投递、不落库，避免 N 节点重复写。
2. **广播扇出先全节点订阅**：公聊「有订阅者的节点 ≈ 所有节点」，优化收益小；「只投有订阅者的节点」需维护房间→节点分布式索引，成本高。等节点数上到几十上百台再优化。
3. **私聊不做主动离线推送**：V3 只保证「消息落 PG + 客户端登录可拉历史」；未读计数/离线推送留给后续 backlog。
4. **Redis TTL = 2~3 倍心跳周期**（如心跳 5s / TTL 15s）：脏映射靠客户端重连覆盖兜底，TTL 不用太短。
5. **单机入口去留**：由「接口抽象」原则解决——不维护两个入口，单机模式 = gateway 挂内存实现、分布式 = 挂真实实现，同一份代码。
