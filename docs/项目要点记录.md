# 项目要点记录

> 用途：记录本项目从需求到上线复盘的完整流程中的要点、决策与计划，方便随时回头复查。
> 维护方式：每完成一次关键对话/决策，就追加一条到「决策记录」，并同步更新「当前状态」和「下一步」。

## 1. 项目定位

一个**真实可用**的 Go 后端 + 网络编程项目，目标是走通完整项目流程（需求 → 设计 → 开发 → 测试 → 上线 → 复盘），最终成为一个**可面试展示**的项目。

## 2. 目标与约束（2026-10-27 确认）

- **真实可用**：不是教学 demo，是真能多人跑起来的东西。
- **北极星目标**：百万级在线（作为演进方向的北极星，不一步到位）。
- **功能范围**：尽可能丰富，但按优先级分批做透（见里程碑规划）。
- **练习重点**：Go 后端、网络编程、并发。
- **最终目的**：可面试项目 —— 能讲清完整流程 + 技术栈 + 系统设计演进故事。

## 4. 里程碑规划（把"百万在线"拆成三步）

- **V1 正确性**：修对现有单机代码、补测试、补鉴权/持久化/时间戳等基础功能 —— 证明「并发安全 + 协议 + 测试」。
- **V2 性能**：压测找瓶颈，优化连接模型/内存/协程泄漏 —— 证明「性能调优 + Go 运行时」。
- **V3 规模（分布式）**：多节点 + 消息中间件 + 网关 + 分片 —— 证明「系统设计」。

## 5. 目标技术栈（终点形态，逐步引入）

- 核心：Go、goroutine/channel/context、自定义 TCP 协议（后续可加 WebSocket）
- 存储：PostgreSQL（持久化）+ Redis（在线状态/会话/Pub-Sub）
- 消息：NATS 或 Kafka（广播解耦，V3 引入）
- 接口：gRPC / REST（管理、鉴权）
- 鉴权：JWT
- 部署：Docker + docker-compose（本地；K8s 可选）
- 可观测：zap（结构化日志）+ Prometheus（指标）+ pprof（性能分析）
- 测试：单元测试 + race 检测 + 压测
- CI：GitHub Actions

- **2026-11-02（V3.3 引入 NATS + 拆接入层）**
  - 新增 `internal/bus`：`Bus` 接口（Publish/Subscribe/Close）+ `Subscription`；内存实现（Publish 先 RLock 快照再锁外回调 handler，避免持锁死锁）+ NATS 实现（JSON 编码 protocol.Message——NATS 自带长度分帧，无需再套协议帧头；Unsubscribe 幂等吞 `ErrBadSubscription`）。契约测试同一套用例跑 Memory + NATS（NATS 不可用则 skip）。
  - 服务端消息投递改走总线：`broadcast`/`broadcastSystem`/`private` 改 `bus.Publish`；`subscribeBus` 注册广播/系统/定向（`subjectNode+node`）三个主题订阅。单机内存 bus 同步回调等价原直接遍历 `sessions`，**行为不变**；换 NATS 后回调改由 NATS 后台协程触发，代码不变（ports & adapters 的收益）。
  - `private` 从本地 `sessions[to]` 升级为 `presence.Node(to)` 定位目标节点 + 定向主题投递，为跨节点私聊铺路。
  - 拆接入层：`internal/server` → `internal/gateway`（`Server`→`Gateway`、`NewServer`→`NewGateway`），`cmd/server` → `cmd/gateway`（单机入口按 V3架构.md 退役）——纯命名重构，行为不变。
  - 节点身份独立成 `-node`（默认回落 `-addr`）：`presence.Join` 与 `subjectNode+node` 改用节点身份而非监听地址，解决挂 LB 多节点同端口（`0.0.0.0:8888`）撞节点 ID 的问题。
  - `main.go` 加 `-bus memory|nats` / `-nats-url` / `-node`，`openBus` 选择后端，默认 memory 向后兼容。
  - 验收：`TestTwoNodesCrossNode` 集成测试——两个 Gateway（node-a/node-b）共用 Redis+NATS，跨节点在线列表 / 公聊广播 / 私聊定向全走通（Redis/NATS 不可用则 skip）。端到端：`-bus nats` 起 server + bench 3 客户端广播丢 0、延迟 ~834µs。

- **2026-11-03（V3.4 网关 + 水平扩展压测）**
  - 新增 L4 TCP round-robin 负载均衡器 `cmd/lb`（轮询转发到后端 gateway）+ `scripts/run-cluster.sh` 一键起多节点集群（LB + N 个 gateway + NATS + Redis + PG）。
  - 多节点压测（连 LB）：1000 客户端 / 10 条广播，2 节点在线分布 500/500（LB 均匀分流）、跨节点广播经 NATS 丢 0、延迟 avg 14.8ms / P50 11.2ms / P99 25.9ms；1 节点对照 avg 15.8ms——NATS 一跳未带来明显延迟惩罚。
  - 诚实结论：1000 客户端远低于单节点上限，**看不出「2 节点容量翻倍」的收益**；水平扩展收益（2×连接容量 + 广播扇出 CPU 减半）要跑到单节点瓶颈才显形，留 V5 中等规模验证。
