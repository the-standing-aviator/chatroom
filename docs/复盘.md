# 复盘 — V1（正确性）

> 用途：V1 里程碑完成后的得失总结。北极星「百万在线」按 V1 正确性 → V2 性能 → V3 分布式 三步走，本文复盘第一步。

## 1. 目标回顾

V1 的唯一目标是**正确性**：把单机聊天室做对、做扎实、可测试。不追求性能（V2）和规模（V3）。

- 北极星：百万在线。
- V1 交付：功能跑通 + 并发安全 + 有测试 + 可排查。

## 2. 成果

| 维度 | 结果 |
|------|------|
| 功能 | FR-1~FR-10 全部完成（公聊/私聊/改名/在线列表/鉴权/时间戳/心跳/持久化/zap/测试） |
| Bug 修复 | P1-1~P1-6 共 6 个 |
| 测试 | protocol / store / server 三层，`go test -race ./...` 全绿 |
| 验收 | 双客户端手工验收通过（登录→公聊→私聊→在线列表→历史） |
| 版本管理 | 7 个 Conventional Commits，每个带 body |

## 3. 关键技术决策（面试可讲的 WHY）

1. **分层 `cmd/internal/{server,protocol,store}`**：入口与业务分离；`internal` 拒绝外部 import，边界清晰。
2. **协议：长度前缀 + JSON 帧**。TCP 是字节流、没有消息边界，必须分帧。相比原来的「换行字符串 + `|` 分隔」，长度前缀能承载任意内容（含换行/分隔符）、JSON 让字段可扩展。这是网络编程的必修课。
3. **store 接口化**：`server` 只依赖 `store.Store` 接口，不关心底层。V1 用 SQLite，V3 换 PostgreSQL 时服务端零改动。
4. **鉴权 bcrypt**：密码不明文存储，哈希加盐。
5. **结构化日志 zap**：替代 `fmt.Println`，为后续接入 Prometheus/告警打基础。

## 4. 踩坑与教训（最有价值的部分）

### 4.1 数据竞态（P1-3）：并发读写同一字段
- **坑**：`rename` 在锁内改 `name`，但 `BroadCast` 读 `name` 不加锁，多协程读写同一字段。
- **教训**：字段级并发读写必须同步（`nameMu sync.RWMutex`）。这类 bug 单测跑一万次也不一定复现，但 `go test -race` 立刻现形。
- **对应**：`TestSessionNameConcurrentAccess`。

### 4.2 越界 panic 崩进程（P1-1）
- **坑**：`strings.Split(msg, "|")[2]` 未校验长度，恶意输入直接 `index out of range`，且无 recover，整个进程崩溃。
- **教训**：① 外部输入永远不可信，先校验；② 单连接的 panic 不该拖垮全局，`handle` 加 recover 兜底。
- **对应**：`TestRouteRejectsBadInput` + `TestHandleRecoverFromPanic`。

### 4.3 优雅关闭（P1-6）：异步 send 被硬关闭丢弃
- **坑**：鉴权失败时 `s.send(error)` 是异步投递到 `sendCh`，`handle` 随即 return 触发 `close()`，旧 `close()` 用 `close(quit)` 让写协程立即退出并关连接，错误消息还没写出就被丢——客户端只看到 EOF。
- **教训**：`close(channel)` 的语义是「不再接收新消息」，`range` 会先把存量消费完再退出，天然实现 flush。关闭连接要等写协程 flush 完。
- **对应**：由端到端测试 `TestHandleLoginWrongPassword` 暴露，修复为优雅关闭 + 写超时。

### 4.4 测试的价值：抓到了光靠眼睛看不到的 bug
P1-6 藏得极深——它不是数据竞态（`-race` 测不出），而是 goroutine 调度时序问题。是端到端测试把它逼出来的。**测试不是证明"代码对"，而是逼代码暴露问题。**

## 5. 不足与改进

1. **无 TLS**：消息明文传输（V1 明确范围外，V2/V3 补）。
2. **密码明文回显**：客户端输入密码可见，应用 `golang.org/x/term` 关闭回显。
3. **写超时是"后补"的**：P1-6 修复时才加 `writeTimeout`，设计阶段就该和 `readTimeout` 对称考虑。
4. **P1-4 丢消息只计数未根治**：队列满丢消息是刻意权衡，V1 只加 `dropped` 计数，真正的背压/断慢连接留 V2。

## 6. V2 展望（下一步）

- **压测**：单机稳定支撑 ≥1000 在线（V1 需求里的性能基线还没测）。
- **连接模型**：每连接一个 goroutine + 两个 channel，在大量连接下的开销。
- **背压**：慢客户端处理（队列满时断连接 vs 动态扩容）。
- **可观测**：Prometheus 指标（在线数、丢消息数、goroutine 数）。
- **pprof**：定位 CPU/内存/协程泄漏。

## 7. 一句话总结

V1 证明的是：**一个能跑、并发安全、有测试、可排查的网络服务长什么样**。下一阶段 V2 要回答「它扛不扛得住」。
