> 用途：把这个项目写进简历、以及在面试里讲透它。简历条目 + 面试追问清单 + 相比同类项目的优势 + 可追加的亮点路线图。

## 1. 项目一句话定位

**Go 分布式实时聊天系统**：从单机 TCP 聊天室起步，演进到「多节点 + NATS 消息总线 + Redis 在线状态 + PostgreSQL 持久化 + 负载均衡」的分布式架构，目标是逐步做到千万级在线。

> 面试开场 20 秒就讲这句。重点是「分布式」「可替换接口」「生产化」三个词。

## 3. 面试追问清单（每个要能白板讲 5 分钟）

这几个点是面试官大概率会顺着简历往下问的，回答要「讲 WHY」而非「讲 what」。

### 3.1 跨节点私聊怎么路由？为什么用 NATS？
- **问题**：用户 A 在节点 1，用户 B 在节点 2，A 给 B 发私聊怎么送达？
- **答**：在线登记表（presence）存「昵称 → 所在节点」，A 发私聊时先查 B 在哪个节点，再经 NATS 按「目标节点 subject」定向投递，由目标节点的 handler 扇出到本地连接。NATS 解决的是「节点间怎么互相发现和转发」，避免各节点两两直连的 O(N²) 网状拓扑。

### 3.2 异步持久化为什么快？怎么保证不丢消息？
- **问题**：广播延迟怎么从 19ms 降到 0.9ms？会不会丢？
- **答**：原来是「落盘成功才广播」，磁盘 I/O 卡在广播主链路上。改成「广播走总线（内存）先扇出、落盘走独立 channel 队列 + saveLoop 协程异步写」，广播延迟不再被磁盘拖累。不丢消息靠「优雅关闭时 flush 队列」：SIGTERM 时先停收新消息、把队列里的消息写完再退出。

### 3.3 私聊隐私怎么在 history 接口泄漏的？怎么修？
- **问题**：讲一个你实际修过的 bug。
- **答**：历史接口 `ListMessages` 原来不按查询者过滤，任何登录用户都能拉到所有人的私聊。修法是给查询加 `viewer` 过滤——公聊（to 为空）所有人可见、私聊只有收发双方可见，而且过滤放在 SQL 里而不是查出来再筛（否则 limit 语义会错，先取 limit 条再过滤会拿到远少于 limit 条的结果）。

### 3.4 为什么把存储/在线状态/消息总线抽象成接口？
- **问题**：为什么这么设计，带来了什么？
- **答**：这是「ports & adapters」——业务逻辑只依赖接口，底层实现可替换。SQLite→PostgreSQL、内存→Redis/NATS 都是「换个实现、业务零改动」，让单机版本和分布式版本共用同一套代码；测试也能用内存 fake 隔离数据库。核心是「面向接口编程，把变化隔离在边界」。

### 3.5 慢客户端怎么处理（背压）？为什么限流？
- **问题**：一个客户端读得慢，会不会拖垮广播？
- **答**：每个会话独立 sendCh，慢客户端不会阻塞别人；系统消息（上下线）走独立通道，不挤占业务消息。限流用令牌桶，因为「公聊广播是 1 进 N 出」——一个人刷屏会放大成 N 倍负载，必须在入口限速。

## 4. 相比同类项目的优势（现状）

大多数「聊天室」简历项目是：单进程、无持久化、无鉴权、无多节点、无测试、无部署。本项目已经具备但别人通常没有的：

| 维度 | 同类项目常见 | 本项目 |
|---|---|---|
| 架构 | 单机 | 多 gateway + NATS + Redis + PG + L4 负载均衡 |
| 持久化 | 内存 / 文件 | SQLite / PostgreSQL，接口可替换 |
| 鉴权 | 无 / 简单 token | JWT + bcrypt + 滑动过期 |
| 传输 | 仅 WebSocket | 自定义 TCP 协议 + WebSocket，共用同一套 conn 抽象 |
| 可靠性 | 无 | 异步持久化 + 优雅关闭不丢消息 + 背压 + 限流 |
| 可观测 | 无 | zap 日志 + Prometheus 指标 + pprof + Grafana + 告警 |
| 测试 | 无 | 单测 + 竞态 + 集成 + 两后端共享契约测试 |
| 部署 | 无 | 多阶段 Docker + docker-compose 一键起 + systemd/nginx |

**结论**：优势不是「聊天室」本身，而是「把聊天室这个载体做成了有真实分布式问题的系统」。面试时反复强调这个定位。

## 5. 可追加的亮点路线图（按性价比排序）

> 按「面试加分 / 工作量」排序，`★` 越多越推荐先做。

| 优先级 | 亮点 | 为什么加分 | 工作量 |
|---|---|---|---|
| ★★★ | **CI/CD（GitHub Actions）**：push 自动跑 build + vet + 单测 + race + 覆盖率 | 「工程化」最直接的信号，绝大多数简历项目没有；还能顺带量化测试 | 低 |
| ★★★ | **测试覆盖率报告**（go test -cover + badge） | 把「测试充分」变成可验证的数字 | 极低 |
| ★★★ | **未读计数 + 已读回执** | 真实的「消息状态」功能，能讲「已读位置用消息 id 游标」的设计 | 中 |
| ★★ | **分布式追踪（OpenTelemetry）**：一条消息 gateway→NATS→gateway 的 trace | 「分布式系统」硬核信号，跨节点追踪是亮点中的亮点 | 中高 |
| ★★ | **TCP 层 TLS 加密传输** | 现在 TCP 是明文，补上能讲「传输安全」，且是真实生产必需 | 低中 |
| ★★ | **压测结果可视化**：把 cmd/bench 的数据做成图表写进 README | 性能用数字说话 | 低 |
| ★ | **消息撤回 / 编辑** | 消息状态机，WeChat 体验，能讲「消息生命周期」 | 中 |
| ★ | **Web Push 离线推送** | 真·离线消息闭环（浏览器关了也能收），但工程量大 | 高 |
| ★ | **消息去重 / 幂等（at-least-once → exactly-once）** | 分布式投递可靠性语义，高级话题 | 中高 |

**建议顺序**：先做 CI + 覆盖率（半天，立刻能写进简历），再做未读计数（功能完整度），最后根据目标岗位决定要不要上 OpenTelemetry（如果投基础设施/后端岗，这个性价比极高）。
