# 设计文档 — 多人实时聊天室（V1）

> 版本：v0.1（2026-10-29）
> 状态：逆向补记（代码已按此设计落地，本文档记录现状与决策依据）
> 关联：需求见《需求.md》；要点/决策见《项目要点记录.md》；问题见《问题与解决方案.md》

## 1. 设计目标与约束

承接 V1（正确性）范围，设计目标优先级：

1. **正确性优先**：并发安全、协议无歧义、可测试（`go test -race` 通过）。
2. **真实可用**：多人真能连、真能聊、重启不丢消息。
3. **为演进留口子**：V1 单机做扎实，但接口/分层要允许 V2（性能）、V3（分布式）平滑升级。

V1 明确不做（详见《需求.md》范围外）：TLS、多房间、分布式、WebSocket。

## 2. 总体架构

### 2.1 分层与目录

```
communicate/
├── cmd/                     # 入口（main 包），只做「装配」，不含业务逻辑
│   ├── server/main.go       # 服务端入口：解析 flag → 建 logger/store → 起 Server
│   └── client/main.go       # 客户端入口：登录 → 菜单 → 收/发循环
└── internal/                # 业务逻辑，不对外暴露
    ├── protocol/            # 通信协议：帧编解码 + 消息结构
    ├── store/               # 持久化：Store 接口 + SQLite 实现
    └── server/              # 服务端核心：连接管理、鉴权、路由、广播
        ├── server.go        # Server：在线表、广播/私聊/改名/在线列表
        ├── session.go       # Session：单连接状态 + 写协程
        ├── handler.go       # handle 读循环 + route 路由
        └── auth.go          # 鉴权（登录/注册）
```

### 2.2 依赖方向（单向，禁止反向）

```
cmd ──► internal/server ──► internal/protocol
                 │
                 └──► internal/store
```

- `cmd` 依赖 `internal/*`，`internal/*` 不依赖 `cmd`（入口可换，业务不变）。
- `server` 依赖 `store` 的**接口**，不依赖 SQLite 具体实现 —— 这是换数据库的接缝。
- `store`、`protocol` 是**叶子层**，不依赖上层，可独立测试。

**WHY 分 `cmd` + `internal`**：Go 惯例。`internal` 阻止外部包 import 业务代码，`cmd` 只留薄薄的 `main`，方便将来加多入口（如 `cmd/admin`）或换部署方式。

## 3. 通信协议

### 3.1 分帧

TCP 是字节流，没有消息边界，必须靠帧头分帧。采用「长度前缀」方案：

```
[4 字节大端 uint32 = 消息体长度 N][N 字节 JSON 消息体]
```

- 单帧消息体上限 `MaxFrameSize = 64KB`（`protocol/protocol.go:19`），防止恶意客户端发超长数据撑爆内存。
- `WriteFrame` / `ReadFrame` 用 `io.ReadFull` 保证读满一整帧，天然处理 TCP 粘包/半包。

**WHY 长度前缀而不是换行分隔**：换行分隔在旧版（`\n` 结尾字符串）下，消息内容里含换行/特殊字符会破坏协议；长度前缀能精确读完整帧，内容可包含任意字节。

### 3.2 消息结构

统一用 `protocol.Message`（JSON），`type` 字段区分类型，其余字段按需出现（`omitempty`）：

| 字段 | 用途 |
|------|------|
| `type` | 消息类型（必填） |
| `name` / `password` | 鉴权（auth） |
| `from` / `to` / `content` | 聊天（chat / private / broadcast） |
| `ts` | 时间戳（Unix 秒） |
| `new_name` | 改名（rename） |
| `users` | 在线列表（who_list） |
| `limit` / `messages` | 历史消息（history） |
| `error` | 错误提示（error） |

### 3.3 消息类型

**客户端 → 服务端**

| 类型 | 说明 |
|------|------|
| `auth` | 登录/注册（name + password） |
| `chat` | 公聊（content） |
| `private` | 私聊（to + content） |
| `rename` | 改名（new_name） |
| `who` | 查看在线列表 |
| `history` | 查看历史消息（limit） |
| `heartbeat` | 心跳保活 |

**服务端 → 客户端**

| 类型 | 说明 |
|------|------|
| `broadcast` | 公聊广播（from + content + ts） |
| `system` | 系统提示（上下线/改名等） |
| `error` | 错误提示 |
| `pong` | 心跳应答 |
| `who_list` | 在线列表（users） |
| `history` | 历史消息响应（复用同名字段，带 messages） |

### 3.4 协议设计决策

- **WHY JSON 而不是自定义二进制**：V1 求正确性与可调试性，JSON 自描述、跨语言、可读日志；性能不是 V1 瓶颈。V2 压测若发现 JSON 编解码是热点，再评估换二进制（protobuf/自定义）。
- **WHY 统一 Message 结构 + type 字段**：所有消息走同一套编解码，新增类型只加字段/常量，不改帧逻辑。

## 4. 并发模型

### 4.1 goroutine 结构（每连接两个 goroutine）

```
            ┌─────────────────────────────────────┐
conn ──────►│ handle goroutine（读循环）            │
            │   读帧 → route 分发 → 广播/私聊/改名   │
            │                                     │
            │   writeLoop goroutine（写）          │
            │   从 sendCh 取消息 → WriteFrame 写出  │
            └─────────────────────────────────────┘
```

- **读**：`handle` 每轮刷新读超时（`readTimeout = 30s`），心跳不断重置它；超时判断线。
- **写**：`writeLoop` 消费 `sendCh`，写失败或收到 `quit` 信号即退出，避免协程泄漏。
- 读写分离，用带缓冲的 `sendCh`（`sendBuffer = 64`）解耦：广播线程只往队列投递，不直接碰网络写。

**WHY 读写分离**：旧版每个用户一个「写协程 + 主读循环」，广播直接 `conn.Write`；现在把「投递」和「写出」拆开，广播路径更快，慢客户端不会卡住别人。

### 4.2 锁与同步原语

| 保护对象 | 锁 | 位置 |
|----------|----|------|
| 在线表 `sessions map` | `srv.mu sync.RWMutex` | `server.go:28` |
| 会话昵称 `Session.name` | `nameMu sync.RWMutex` | `session.go:17` |
| `close` 幂等 | `sync.Once` | `session.go:22` |
| 写协程退出信号 | `quit chan struct{}` | `session.go:21` |
| 丢弃计数 | `atomic.Int64` | `server.go:31` |

- 读多写少用 `RWMutex`（广播遍历在线表是高频读）。
- 昵称独立加锁（`nameMu`），修复旧版 `Name` 字段竞态（P1-3）。

### 4.3 背压与丢消息策略

`Session.send` 用**非阻塞投递**：队列满时**丢弃并计数**（`dropped.Add(1)`），每 30s 日志输出 `dropped_messages`。

**WHY 允许丢弃**：这是刻意的权衡 —— 一个慢客户端若阻塞广播，会拖垮所有人；用非阻塞投递 + 丢弃，保证广播的实时性，代价是极端情况下个别慢客户端丢消息。V1 接受这个代价并**计数上报**（可见、可度量），V2 再考虑背压/断慢连接/动态扩容队列。

## 5. 持久化

### 5.1 Store 接口抽象

`store.Store` 接口（`store/store.go`）定义了服务端需要的全部持久化能力：

```go
type Store interface {
    CreateUser(name, passwordHash string) error
    GetUser(name string) (User, error)
    SaveMessage(m Message) error
    ListMessages(limit int) ([]Message, error)
    Close() error
}
```

服务端只依赖这个接口，不 import SQLite 具体类型。

**WHY 接口抽象**：V1 用 SQLite 起步（简单、零部署），但接口已留好，V3 换 PostgreSQL 只需新增一个实现 + 改入口注入，`server` 包一行不动。这也是「依赖倒置」的体现。

### 5.2 SQLite 实现

- 驱动 `modernc.org/sqlite`（纯 Go，无 cgo，跨平台编译简单）。
- `SetMaxOpenConns(1)`：SQLite 是单写者，限制连接数避免并发写触发 `database is locked`（`sqlite.go:25`）。
- 数据库路径由 `-db` flag 指定，默认 `chat.db`。

### 5.3 表结构

```sql
users(
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT NOT NULL UNIQUE,       -- 昵称唯一
    password_hash TEXT NOT NULL,              -- bcrypt 哈希，不存明文
    created_at    INTEGER NOT NULL
);
messages(
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    type    TEXT NOT NULL,                    -- chat / private
    "from"  TEXT NOT NULL DEFAULT '',
    "to"    TEXT NOT NULL DEFAULT '',
    content TEXT NOT NULL DEFAULT '',
    ts      INTEGER NOT NULL
);
CREATE INDEX idx_messages_ts ON messages(ts);
```

- `from`/`to` 是 SQL 关键字，故加引号。
- 历史查询：先按 `id DESC` 取最近 N 条，再 `ASC` 返回，保证「旧→新」的时间顺序（`sqlite.go:95-99`）。

## 6. 鉴权设计

流程（`server/auth.go`）：

1. 连接建立后，先进入鉴权阶段（`authTimeout = 10s`），客户端须先发 `auth` 帧。
2. 昵称不存在 → 视为**注册**：`bcrypt.GenerateFromPassword` 存哈希。
3. 昵称已存在 → **校验密码**：`bcrypt.CompareHashAndPassword`。
4. 鉴权通过 → `setName`，随后 `addSession` 校验**在线唯一性**（昵称重复在线则拒绝）。

**WHY bcrypt**：密码不明文存储；bcrypt 自带加盐 + 高成本哈希，抗暴力破解。**WHY 注册/登录合一**：V1 简化交互，一个 `auth` 帧同时覆盖注册和登录，减少协议类型。

## 7. 关键设计决策与权衡

| 决策 | 选择 | WHY |
|------|------|-----|
| 分帧 | 长度前缀 + JSON | TCP 无边界需分帧；JSON 可读可调试，性能 V2 再优化 |
| 分层 | cmd / internal/{server,protocol,store} | 依赖单向，可测试，可换实现 |
| 每连接模型 | 读写双 goroutine + 带缓冲队列 | 解耦收与发，慢客户端不阻塞广播 |
| 背压 | 非阻塞投递 + 丢弃计数 | 保广播实时性，代价可度量，V2 再演进 |
| 存储 | 接口抽象 + SQLite 实现 | V1 简单，接口留 PostgreSQL 升级口子 |
| 鉴权 | bcrypt + 注册登录合一 | 不明文存密码，协议最简 |
| 容错 | `recover` 兜底单连接 | 单连接 panic 不崩进程（P1-1） |
| 可观测 | zap 结构化日志 + 周期 stats | 上下线/广播/丢消息可追踪，V2 接 Prometheus |

## 8. 为 V2 / V3 预留的演进点

- **V2（性能）**：压测定位瓶颈；`dropped` 计数 → Prometheus 指标；JSON → 更紧凑协议；队列背压策略（断慢连接/动态扩容）。
- **V3（分布式）**：`store.Store` 换 PostgreSQL；广播经消息中间件（NATS/Kafka）解耦多节点；会话表从进程内 `map` 迁到 Redis；网关 + gRPC/REST 管理面。
