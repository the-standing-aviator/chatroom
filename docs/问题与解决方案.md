## 开发阶段前盘点（V1 已修复，2026-10-29 确认）

> 以下 5 个问题在「代码分层重构」中已全部修复，状态 🟢。修复后的新代码位置见各条。

### 🟢 P1-1 私聊命令缺字段会 panic（已修复）
- **原位置**：`user.go` `DoMsg` 私聊分支
- **原现象**：发送 `to|张三`（无消息内容）时，`strings.Split(msg,"|")[2]` 越界，触发 index out of range panic，导致**整个进程崩溃**。
- **根因**：直接用下标取第 3 段，未校验切分后长度；且 Handler 协程没有 recover 兜底。
- **修复**：协议改为 JSON 帧，私聊字段为 `to`/`content`，在 `internal/server/handler.go` 的 `route` 中校验 `m.To == "" || m.Content == ""` 后返回错误（不再有数组越界）；同时 `handle` 加了 `recover` 兜底，单连接 panic 只影响该连接。

### 🟢 P1-2 客户端 -ip/-port 参数被忽略（已修复）
- **原位置**：`client.go` `main()`
- **原现象**：`flag.Parse()` 解析了参数，但 `NewClient("127.0.0.1", 8888)` 硬编码，命令行传参无效。
- **根因**：解析后的变量没被使用。
- **修复**：客户端重写为 `cmd/client/main.go`，用 `flag -addr`（如 `-addr 127.0.0.1:8888`）并传给 `net.Dial`。⚠️ 参数形态由 `-ip`/`-port` 合并为单个 `-addr`。

### 🟢 P1-3 `Name` 字段数据竞态（已修复）
- **原位置**：`user.go` / `server.go` `BroadCast`
- **原现象**：rename 在锁内改 `this.Name`，但 `BroadCast` 等读 `user.Name` 不加锁，多协程读写同一字段。
- **根因**：字段级并发读写未同步（`go test -race` 可复现）。
- **修复**：`internal/server/session.go` 用 `nameMu sync.RWMutex` 保护 `Session.name`，`Name()`/`setName()` 均加锁；在线表 `sessions map` 由 `server.go` 的 `mu sync.RWMutex` 统一保护。

### 🟢 P1-4 `send` 队列满时静默丢消息（已修复，V1 方案）
- **原位置**：`user.go` `send()`
- **原现象**：缓冲满时消息被直接丢弃，发送方无感知。
- **根因/权衡**：用非阻塞投递避免慢客户端拖垮广播，是刻意的权衡，但代价是丢消息。
- **修复（V1 方案落地）**：`session.go` 队列满时 `dropped.Add(1)` 计数，`server.go` 每 30s 用日志输出 `dropped_messages`。V2 再考虑背压 / 断慢连接 / 动态扩容队列。

### 🟢 P1-5 无鉴权、明文传输、无持久化、无时间戳（已修复，V1 范围内）
- **原现象**：任意客户端可连接并冒充任意昵称；消息不落盘，重启全丢；消息无时间戳。
- **修复**：
  - 鉴权：`internal/server/auth.go` 用 bcrypt 存/校验密码，注册登录合一。
  - 持久化：`internal/store/sqlite.go` 落盘 SQLite（users + messages 表）。
  - 时间戳：协议消息统一带 `ts` 字段。
  - 明文传输 / TLS：仍为 V1 范围外（见《需求.md》），暂未做。

## 开发阶段（补测试时发现）

### 🟢 P1-6 鉴权失败时错误消息丢失（已修复，优雅关闭）
- **现象**：登录密码错误、昵称/密码为空、非 auth 消息、重名等鉴权失败场景，客户端收到 EOF（连接直接断开），而非对应的错误提示。
- **根因**：`authenticate` 失败时 `s.send(error)` 是异步投递到 `sendCh`；`handle` 随即 return 触发 `close()`。旧 `close()` 用 `close(quit)` 让 `writeLoop` 立即退出并 `conn.Close()`，`sendCh` 里的错误消息还没被写出就被丢弃。
- **修复**：`session.go` 把 `close()` 改为优雅关闭——`close(sendCh)` 通知"不再有新消息"，`writeLoop` 改用 `for m := range s.sendCh` 把剩余消息 flush 完再关连接，连接关闭职责收拢到 `writeLoop`；`handler.go` 去掉 `handle` 里的 `conn.Close()`。同时加 `writeTimeout`（10s）写超时防慢客户端卡死写协程，`send` 加 recover 兜底防 send-on-closed-channel。由端到端测试 `TestHandleLoginWrongPassword` 暴露。

## V1 收尾

### 🟢 FR-10 自动化测试已完成
- **现状**：`protocol` / `store` / `server` 三个包均有 `_test.go`，`go test -race ./...` 全绿。
- **覆盖**：protocol（帧编解码往返/非法大小/缺 type/半包/粘包/超限）、store（注册查重/历史顺序与 limit/空库）、server（注册登录/密码错误/非法输入/并发竞态/私聊/改名重名/recover 兜底，共 8 个用例）。

### 🟢 客户端主动退出时显示「连接已断开」（已修复）
- **现象**：客户端主动选 0 退出时，`receive` 协程读到连接关闭，打印 `[连接已断开] use of closed network connection`，误导用户以为是异常断开（手工验收时发现）。
- **根因**：主动退出（main 的 `defer conn.Close()`）与 `receive` 协程的 `ReadFrame` 竞争，后者把"连接被关闭"统一当成异常处理，没有区分"主动关闭"与"异常断开"。
- **修复**：`Client` 加 `done` channel，主动退出时 `close(done)`；`receive` 读到错误后先 `select done`——已关闭则静默 return，否则按异常断开打印并退出。

## V2 性能

### 🟢 P2-1 广播路径同步 SQLite 写拖慢延迟（已修复，异步持久化）
- **现象**：压测（`cmd/bench`）测得广播延迟 P50 ~19ms、P99 ~38ms，而 localhost 回环应亚毫秒。
- **定位过程**（打点二分的完整链）：
  1. 先怀疑 TCP Nagle：给连接加 `SetNoDelay(true)` 重测，延迟不降反微升 → 假设被推翻，排除。
  2. 最小规模对照（`-n 2`）：延迟仅 0.6ms → 说明是「并发上去后才出现」，非单条消息的固定开销。
  3. 在 `broadcast` 里打点二分：`send_loop`（遍历投递）27µs vs `save_db`（SQLite 写）25ms → 锁定 SQLite。
- **根因**：`broadcast`/`private` 在广播后「同步」调用 `SaveMessage`。SQLite 默认 rollback journal + `synchronous=FULL`，每条 INSERT 是一个自动事务，要写 journal + 两次 fsync（强制刷盘），WSL2 上单次 ~25ms，直接拖累广播延迟。
- **修复**：
  - 异步持久化：新增 `saveCh`（缓冲 1024）+ `saveLoop` 后台落盘，`broadcast`/`private` 改为 `enqueue` 入队即返回，广播只碰网络与内存，延迟降到 ~0.9ms。
  - 优雅关闭：进程收到 SIGINT/SIGTERM 时 `Shutdown`——停 Accept → 关 session → 等 handle 退出 → `close(saveCh)` → 等 saveLoop flush 完再退出，正常关闭不丢消息。
  - `saveOne` 加 recover 兜底，单条落盘 panic 不崩 saveLoop（进程级 goroutine）。
- **权衡**：进程在「已广播未落盘」窗口内被强杀（kill -9 / 断电）会丢最近几条消息，这是异步持久化的固有代价。
- **验证**：压测延迟 19ms → 0.9ms（约 20 倍）；SIGTERM 下 200 条积压消息全部落盘、进程 exit 0。

### 🟢 P2-2 压测延迟虚高：bench 200ms 读超时 artifact（已修复）
- **现象**：1000 连接广播延迟端到端测出 P50 ~118ms，scaling 曲线 500→1000 超线性暴涨 7 倍，看起来像服务端规模化瓶颈。
- **定位过程**（打点二分 + wall-clock 对齐）：服务端 `fanout`（遍历投递）134µs、`writewait`（投递→写 socket）~1.2ms，加起来才 ~2.8ms；但「服务端投递 → bench 收到」高达 ~122ms，而 bench 的 `ReadFrame` 一旦调用只等 3µs——说明数据早已躺在 socket 里，receive 隔了 ~122ms 才去读。
- **根因**：bench 的 receive 用 `SetReadDeadline(200ms)` + 空转来周期性检查 `done` 退出。广播到达后若 receive 正处超时空转，数据躺在 socket 里等下一轮才读，虚高延迟。真实客户端「一直阻塞读」，不存在这段等待。
- **修复**：receive 改为一直阻塞读，收尾 `close conn` 打断 ReadFrame（读错误退出）。验证：n=1000 msg=1 延迟 118ms → 2.8ms。
- **教训**：压测端到端数字要打点验证，别直接信——测量工具自身的调度/超时策略会引入 artifact，把工具的问题当成服务端的问题。

### 🟢 P2-3 登录上下线广播积压挤占 sendCh（已修复，系统消息分级）
- **现象**：msg=1 端到端延迟 settle=0 时 54ms，settle 3s 后降到 2.81ms——差的 ~50ms 是登录刚结束时的排队。
- **根因**：1000 客户端登录，每登录 1 个就 `broadcastSystem("已上线")` 给所有在线者，累计 ~50 万条上下线消息。它们与 chat 共用 `sendCh`(64)，登录风暴让 chat 排在上下线消息后面被拖慢。
- **修复**：系统消息分级——`Session` 加独立 `sysCh`（缓冲 8，比 `sendCh` 小），上下线/改名广播改走 `sendSystem`（非阻塞、满则静默丢、不计数）；`writeLoop` 重写为两级 select，业务消息（`sendCh`）优先，系统消息只在业务队列空时才写。登录风暴的上下线广播被限制在每连接 8 条的小缓冲里，多余直接丢，`sendCh` 保持干净，chat 不再排队。
- **权衡**：系统消息是「尽力而为」——风暴时部分上下线广播会被丢弃（客户端看不到某几条「已上线」），换来 chat 延迟不被系统消息拖慢。可接受，因为上下线提示本就是可丢失的。

### 🟢 P2-4 登录风暴时 SQLite 单连接成瓶颈（已解决，V3.1 换 PostgreSQL）
- **现象**：1000 并发注册时，pprof goroutine 快照显示 707 个协程阻塞在 `database/sql.(*DB).conn`（355 卡 `GetUser` + 352 卡 `CreateUser`），注册吞吐被压在单连接串行上。
- **根因**：`internal/store/sqlite.go` 里 `db.SetMaxOpenConns(1)` 把连接池压成单连接。SQLite 单写模型 + 并发注册（每个注册都要 `GetUser` 查重 + `CreateUser` 插入）在同一连接上串行排队，其余协程全部阻塞等待拿连接。
- **修复（V3.1）**：换 PostgreSQL——新增 `internal/store/postgres.go` 实现同一 `Store` 接口（pgx/v5/stdlib 驱动），不再 `SetMaxOpenConns(1)`，交给连接池并发读写；`main.go` 加 `-store` 切换后端。验证：连 PG 起 server，注册吞吐 153.9/s（SQLite 单连接约 45/s），广播延迟 ~750µs。
- **定位方法**：`curl /debug/pprof/goroutine?debug=1` 快照 + 按 `store` 函数名聚合，阻塞点集中暴露在 `database/sql.(*DB).conn`。这正是「Prometheus 探测 → pprof 定位」的完整闭环——指标告诉你「有异常」，pprof 告诉你「在哪」。

## 开发环境踩坑

### 🟢 Windows 的 Go 无法在 WSL 文件系统上构建（RLock 错误）
- **现象**：在 Windows 侧（Git Bash）对 `\\wsl.localhost\...` 路径跑 `go build`/`go get`，报 `RLock ...\go.mod: Incorrect function`。
- **根因**：Windows 版 Go（`C:\Program Files\Go`）需要 Windows 文件锁，而 WSL 的 9P 文件系统（`\\wsl.localhost` UNC 路径）不支持这套锁语义。
- **修复**：进 WSL 内部用 Linux 版 Go（`/usr/local/go/bin/go`）跑构建/测试/依赖，如 `wsl.exe -d Ubuntu-24.04 -- bash -lc 'cd /home/never/go-projects/communicate && /usr/local/go/bin/go test ./...'`。⚠️ 别在命令里用 `$PATH` 拼接（外层 shell 会先展开含 `(x86)` 的 Windows PATH 导致语法错），直接写绝对路径。

### 🟢 Docker Desktop 未给 WSL 开集成 / 引擎未启动（已解决）
- **现象**：WSL 里 `docker` 报「could not be found in this WSL 2 distro」；Windows 侧 `docker info` 报连不上 npipe（找不到 dockerDesktopLinuxEngine）。
- **根因**：Docker Desktop 默认不给 WSL 发行版开集成；且引擎未启动时 npipe 不存在。
- **修复**：启动 Docker Desktop，Settings → Resources → WSL Integration 勾选 Ubuntu-24.04 → Apply & Restart。之后 WSL 内 `docker compose up -d` 直接可用。另：`wsl.exe` 经 Git Bash 调用时开头那行 `wsl: ...` 乱码是 localhost 转发的 UTF-16 提示被误读，无害。

## V3 分布式

### 🟢 P3-1 多节点下 PostgreSQL 连接打满报「too many clients」（已修复，连接池上限）
- **现象**：多节点 gateway 共享同一 PG 实例压测时，报 SQLSTATE 53300「too many clients / connections」。
- **根因**：`database/sql` 不设 `SetMaxOpenConns` 时默认连接池无上限，高并发下每个节点开满连接，撞上 PG 默认 `max_connections=100`。
- **修复**：`internal/store/postgres.go` 设 `SetMaxOpenConns(40)` / `SetMaxIdleConns(40)` / `SetConnMaxLifetime(30m)`——上限取 40 给多节点部署留余量（2 节点共 80 < 100），超出部分在池内排队而非报错；ConnMaxLifetime 防 PG 侧断开的死连接被复用。

### 🟢 P3-2 压测「1880 丢消息 + online 抓 0/0」是 harness 编排 artifact（已解决，非 gateway bug）
- **现象**：2 节点压测出现「1880 条消息丢失」、metrics 在线数一度抓不到（0/0），像 gateway 丢消息。
- **定位链**：
  1. 「user online」日志 584 ≠ 1000 → 实为 zap 生产日志采样（见 P3-3），非真实偏差。
  2. 埋点 bc_received/bc_fanout 计数器 → NATS 把 10 条广播都送到两节点（各 10），总扇出 8120 = bench 实收数 → **NATS 与 sendCh 无丢**，只有 812 个 session 在广播时还在表里（188 缺失）。
  3. 发现 Redis presence 残留 188 条、全在 node-0 → 是**上一轮**残留的在线登记，与本轮固定昵称 `bench-0..999` 撞名，被 HSetNX 判「该用户已在线」拒掉 → bench 误判丢消息。
- **根因**：压测 harness 两个编排缺陷——(a) 跑前没清空 presence，(b) 关停用 `pkill` 发 SIGTERM 后**不等待**优雅退出，`Shutdown`（含 `presence.Leave`）被中断，残留在线登记。
- **修复**：harness 跑前 `DEL presence` + 关停后等 gateway 真正退出。修后压测丢 0、500/500 均匀分布。
- **教训**：分布式压测的「丢消息」先查环境/编排（残留状态、固定命名、关停时序），别急着怀疑业务代码——这是「测量 artifact」在分布式态的翻版（对照 P2-2）。

### 🟢 P3-3 观测与错误暴露三处小修（已修复）
- **zap 生产日志采样**：`zap.NewProduction()` 默认 `Sampling{Initial:100, Thereafter:100}`，重复日志行超阈值后会被丢弃——本次诊断中曾把「user online」计数少（584 vs 1000）误当成真实偏差。观测型日志（如 NATS 慢消费）改用标准库 `log` 绕过采样。
- **NATS slow consumer**：订阅方处理不过来时 NATS 客户端会静默丢消息，之前完全无感知。加 `nats.ErrorHandler` 在 `ErrSlowConsumer` 时打日志 + 记录 `sub.Dropped()`。
- **presence.Leave 静默吞错**：之前 `_ = Leave(...)` 吞错，一旦 Redis 抖动导致注销失败，残留在线登记会让同名用户之后永远「该用户已在线」。改为记 error 日志（`internal/gateway/server.go` `removeSession`）。
